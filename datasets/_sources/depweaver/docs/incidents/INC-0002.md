# INC-0002: `proof rejected for 7f3a…` three times in a row, three different problems

Severity: low (no bad deploy). Duration: one afternoon, then a week of
argument. Status: closed (ADR-0004).

## Symptoms

* `tools/verify_lock.py` failed on a lockfile that had just been re-locked:
  `invalid 7f3a…c2 chosen releases are not in canonical order`.
* The operator re-sorted the proof's `chosen` list by hand to match what the
  guide describes, re-enveloped the proof, and ran the tool again:
  `invalid 7f3a…c2 catalog digest is stale`. Same hash. The operator read this
  as "my re-sort did not take" and spent two hours on the sort.
* After re-locking against the current catalog the tool failed a third time:
  `invalid 7f3a…c2 missing justification for widget 3.1.0`. Same hash again.
  The operator now suspected the hash itself and started comparing it with
  the proof envelope checksum, which is a different number and always will
  be.

## What was actually wrong

Three things, independently:

1. The proof had been produced by a script that sorted `chosen`
   alphabetically. The canonical order is the install order (ADR-0001).
2. The catalog export on the operator's machine was a day older than the one
   the proof had been produced under (ADR-0003).
3. The re-lock was done with a locally patched prover that skipped yanked
   versions when building the preferred set. `widget 3.1.0` is yanked; the
   proof needs a `yanked` justification for it all the same (SPEC P2, P3).

None of the three was visible from the hash, because the hash is the digest
of the lockfile as presented, and the lockfile was the same file all
afternoon. All three were visible from the reason.

## Resolution

No code change to the verifier: it behaved as designed. The design was
written down (ADR-0004) so that the next operator knows that:

* the exception type and the hash are the same for every cause;
* the verifier reports the first failing check in a fixed order, so fixing
  one cause reveals the next with an identical-looking line;
* the thing to read is the reason.

The guide's section "Proofs: what is inside and what is checked" now lists
the check order and the reason text for each.

## Lessons

* When a tool prints the same hash after your fix, that does not mean the
  fix did nothing. It means the artefact is the same; read what it says about
  the artefact.
* Do not sort the chosen list by hand. Run `tools/relock.py --canonical
  --prove` and let it produce the proof; then run `tools/verify_lock.py` with
  `--expect` and the digest relock printed.
