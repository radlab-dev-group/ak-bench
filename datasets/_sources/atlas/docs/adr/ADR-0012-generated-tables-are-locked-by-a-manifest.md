# ADR-0012: The generated tables are locked by a manifest, and the lock is checked by a tool

- Status: accepted
- Date: 2026-09-28
- Concerns: `schema/tables.json`, `src/atlas/tables.py`, `schema/MANIFEST`,
  `tools/gen_tables.py`, `tools/verify_goldens.py`; `SPEC.md` 10.2, 10.9, 10.10

## Context

`src/atlas/tables.py` has said "GENERATED FILE -- DO NOT EDIT" at its top
since the schema document existed, and has been edited by hand at least four
times anyway. Each time the edit was reasonable in isolation — a column
width, an index, a reader-accepts tuple — and each time it was taken back by
the next regeneration, or worse, was *not* taken back because nobody
regenerated and the document and the module drifted apart for months.

The README still describes the module as regenerated by
`python -m atlas.tables --write`. That entry point reports drift and writes
nothing; its `--write` flag has never done anything. That is how the hand
edits got in: the tool people were told to run did not exist, so they edited
the output.

With schema evolution (`SPEC.md` §10) the generated module gains a new
responsibility — `LAYOUTS`, the declaration the evolution code reads — and a
drift between document and module becomes a correctness bug in the read path
rather than a cosmetic one.

## Decision

1. `tools/gen_tables.py` is **the** generator. It renders the whole module
   from the document, deterministically, and nothing else writes
   `src/atlas/tables.py`.
2. `--lock` rewrites the module and writes `schema/MANIFEST`: the schema
   version, the generator version, and the sha256 of the document and of the
   generated module.
3. `--check` regenerates in memory and exits non-zero unless the module on
   disk is byte-identical to the generator's output **and** the manifest
   records exactly those digests. The messages are stable:
   `TablesDrift(...)`, `ManifestMissing(...)`, `ManifestMismatch(...)`.
4. `tools/verify_goldens.py` is the second half of the lock: it recomputes
   every golden under `schema/goldens/` from the code and the fixed rows and
   prints one stable line per golden — `OK`, `GoldenMismatch(...)`,
   `NotImplemented(...)`.
5. The procedure that ties them together is written in exactly one place,
   `docs/schema-evolution.md`. The README is not updated to describe it and
   keeps its old story on purpose: a reader who stops at the README is a
   reader who will hand-edit the module, and the lock exists to catch exactly
   that reader.

## Consequences

- A tree in which `tables.py` was edited by hand fails `--check` even when
  the edit is "the same as what the generator would produce" — because it is
  never quite the same, and when it is, the manifest still disagrees.
- A tree in which the document was changed and the module regenerated but
  the manifest was not rewritten also fails. Regenerating without locking is
  the new way to get it wrong, and the check names it.
- The hidden acceptance tests of every task that touches the schema run
  `gen_tables.py --check` and `verify_goldens.py` themselves, from the
  workspace root, and compare the module against `--stdout`. Passing them by
  any route other than the procedure is not a route.
- The generator version in the manifest lets a future template change be
  told apart from a hand edit: "your generator is older than the lock" is a
  different message from "mismatch".
